# Rafi 1.0.6 — укрепление многоклубной работы (промежуточная сборка)

## Изменено
- Один администратор может быть назначен нескольким клубам/филиалам через Менеджер клубов. Один логин, переключение филиала в верхнем списке. Основной клуб сохраняется в `app_user.club_id`; дополнительные права в `admin_club_access`.
- Проверка доступа к API филиала выполняется на сервере, а не только через интерфейс.
- Конкурирующие операции бронирования сериализуются блокировкой записи клуба в транзакции БД (`PESSIMISTIC_WRITE`), вместо локального `ReentrantLock` Java. Подходит для нескольких экземпляров сервера, использующих одну БД.
- Планировщик завершения бронирований повторно проверяет статус внутри транзакции.
- Добавлены ограничения размера и точности денежных значений для каталога и финансов банкета.
- Запрещено удалять клуб, пока он назначен как дополнительный филиал администратора.

## Не выполнено в этом пакете / требуется дальнейшая работа
- Полная миграция H2 -> PostgreSQL и Flyway (существующая H2 с данными должна мигрировать отдельно, иначе есть риск потери данных).
- Полный перенос бизнес-логики в сервисы, переделка PDF, разбиение index.html, полноценная поддержка часовых поясов разных филиалов.
- Полная проверка всех API на изоляцию, интеграционные тесты с параллельными транзакциями, Maven-сборка и браузерное тестирование: не выполнены в доступной среде.
- Защита cookie secure должна включаться только в production при HTTPS. Пример в application-prod.properties.
- Не публикуйте приложение в интернет до дополнительной проверки безопасности.

## Важное замечание
Сделайте копию папки `data` и исходного проекта перед запуском. Hibernate с `ddl-auto=update` создаст таблицу `admin_club_access` в H2. Существующие учётные записи продолжат иметь доступ к своему основному клубу. Добавьте филиалы разработчиком через Менеджер клубов.
